# Native TikTok app method

`internal/tiktokapp` implements device registration, encrypted SDK seed acquisition, request signing, feed/detail requests, cookies and media routing in Go. Its cryptographic tests use independently generated vectors from the original Node implementation, including all eight signing variants. The production service invokes no Python or JavaScript interpreter.

`internal/identity` owns the PostgreSQL-backed, RAM-resident identity pool. Existing `scrap_proxies` and `scrap_identities` rows remain compatible. Startup prepares ten permanent identity slots per proxy before opening the HTTP listener, reusing healthy registrations and registering missing slots; it fetches no signing seeds. One worker per proxy waits ten seconds after each preparation attempt before starting the next. During normal operation, signing seeds are fetched on demand before a signed request, when missing or at least one hour old, and recovery also happens on demand. RAM holds the authoritative state. A background writer saves completed operations' sessions, assignment counts and health to PostgreSQL, so requests never wait for it. One process owns a schema. Database outages and stalled saves do not stop identity work: the writer reconnects, ends its own orphaned server connection if it still holds ownership, and saves the latest RAM state. Ownership taken by another process, or another writer occupying an identity's proxy slot, stops the pool and the process exits for a supervised restart.

Existing API routes retain their contracts; GET/POST `/v1/tiktok/identities/preparations` adds preparation status and control. Supply `DB_URL` for the required TikTok app identity pool. Proxies can be bootstrapped from `PROXY_FILE` or loaded from the database. New identities use the [Pixel/Samsung device catalog](device-catalog.md); healthy saved devices retain their existing profile.

Each used identity retains its protocol client and cookie jar in RAM. Video selection ranks API-reported resolution, frame rate, and bitrate without CDN rendition probes. Downloads keep one identity lease across fallback URLs. Telegram preparation shares that lease across the video and thumbnail or all slideshow images, downloads related media concurrently, and records one completion checkpoint before any upload completes. A single video can start uploading while it downloads; byte-range parts reuse the CDN address that the play request redirected to. Waiting for an identity does not reserve global download capacity. While a delivery waits for the identity that extracted its post, new extractions use other identities, so the delivery runs as soon as that identity is free. Each delivery prepares at most `TELEGRAM_PREPARATION_CONCURRENCY` media items at once (default 32), in addition to optional thumbnail work; download and image-conversion limits remain global. Recovery cancels and joins preparation workers, releases first-attempt media, aborts any upload still streaming it, and prepares media again, so Telegram receives one complete request; losing schema ownership remains fatal.

Account login is optional. `TIKTOK_SESSION_ID` supplies the raw `sessionid` cookie value at startup, through the environment or `.env`. It stays in memory and is never written to PostgreSQL. An unset or empty value disables account fallback. Restart to change the account. Cookie files are not read, and previously stored account credentials are not loaded.

Detail and app media requests start anonymously. Explicit age or login restrictions, private-content statuses, and regional restrictions trigger an authenticated retry. The session token is sent only to HTTPS TikTok app endpoints under `/aweme/`. The `sid_tt` bridge from web cookies to app requests follows the [yt-dlp TikTok extractor](https://github.com/yt-dlp/yt-dlp/blob/master/yt_dlp/extractor/tiktok.py). Authenticated requests use a separate cookie jar, so their response cookies cannot enter the persisted anonymous device session. Registration, signing-seed requests, feed requests, and unrelated CDN requests do not receive the account token. Failed account access returns the restriction error without penalizing the device's health.

Cookie rotations and deletions apply within an authenticated app request and its redirects. Deleted or expired cookies are not restored from the configured token during that request. A rejected account login preserves the original content restriction; rate limits and service failures retain their normal error handling.

Protocol, persistence and API checks run through `go test -race ./...`. Set `TIKTOK_APP_TEST_DB_URL` for isolated database tests. Opt-in live checks use `TT_SCRAP_LIVE_APP=1` with `go test -run TestLive -v ./internal/platform`. Live app checks use the configured service database and can lazily register an identity.

The [migration notes](migration.md) describe deployment changes from the Python release. The production and test toolchains use Go; the original Node signing vectors remain as JSON fixtures.
